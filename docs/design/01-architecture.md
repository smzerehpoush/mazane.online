# معماری مظنه آنلاین

## ۰. تصمیم محوری محصول

تحقیق ۰۱ یک عدد را تأیید کرد که کل طراحی را تغییر می‌دهد:

> قیمت پایه‌ی هر چهار پلتفرم اصلی در یک لحظه در **۰٫۰۸٪** همدیگر است،
> ولی کارمزد رفت‌وبرگشتشان از **۱٪ تا ۲٫۴٪** فرق می‌کند.

یعنی محصولی که «قیمت لحظه‌ای طلا در پلتفرم‌ها» را نشان بدهد، عملاً چهار عدد
تقریباً یکسان کنار هم می‌گذارد و **هیچ ارزشی تولید نمی‌کند**. کاربر نگاه می‌کند،
می‌بیند همه یکی‌اند، و برنمی‌گردد.

**مظنه آنلاین باید قیمت مؤثر را مقایسه کند، نه قیمت اسمی.** یعنی عددی که کاربر
واقعاً می‌پردازد یا می‌گیرد، با احتساب کارمزد و حداقل سفارش.

این تصمیم مستقیماً به مدل داده تحمیل می‌کند که **کارمزد یک شهروند درجه‌یک باشد،
هم‌رتبه‌ی قیمت** — نه یک فیلد جانبی در جدول محتوا. اکثر خطاهای طراحی در این حوزه
از اینجا شروع می‌شود که کارمزد را «محتوای ثابت» فرض می‌کنند در حالی که تغییر
می‌کند و منبعش هم برای هر پلتفرم فرق دارد.

## ۱. فرمول‌های هسته

با `mid` = قیمت پایه هر گرم به تومان، `f_buy` و `f_sell` = کارمزد اعشاری:

```
قیمت مؤثر خرید   = mid × (1 + f_buy)
قیمت مؤثر فروش   = mid × (1 − f_sell)
هزینه رفت‌وبرگشت = 1 − (1 − f_sell) / (1 + f_buy)
```

با اعداد تأییدشده‌ی تحقیق:

| پلتفرم | f_buy | f_sell | هزینه رفت‌وبرگشت |
|---|---|---|---|
| وال‌گلد | ۰٫۵٪ | ۰٫۵٪ | **۰٫۹۹۵٪** |
| میلی | ۰٫۵٪ | ۰٫۵٪ | **۰٫۹۹۵٪** |
| طلاسی | ۱٪ | ۱٪ | **۱٫۹۸٪** |
| گلدیکا | ۱٫۲٪ | ۱٫۲٪ | **۲٫۳۷٪** |

روی یک معامله‌ی ۱۰۰ میلیون تومانی این یعنی اختلاف **۱٫۴ میلیون تومان** بین
بهترین و بدترین. این تنها عددی است که کاربر را به کلیک وامی‌دارد و کل صفحه‌ی
اصلی باید حول آن ساخته شود.

گلدیکا این رابطه را در API خودش تأیید می‌کند (`buy = mid × 1.012` دقیقاً)، پس
فرمول حدس نیست — با داده‌ی واقعی صحت‌سنجی شده.

## ۲. مدل داده

### ۲.۱ چرا مدل `Asset` میلی کافی نیست

کرالر میلی هر قیمت را با `Source × AssetType × Currency × Tag` می‌شناسد. برای
میلی درست است چون فقط یک قیمت مرجع می‌خواهد — حتی در گلدیکا میانگین خرید و فروش
را می‌گیرد و ذخیره می‌کند. برای ما این **دقیقاً همان چیزی است که نباید دور ریخته
شود**. دو تغییر لازم است:

1. بعد **`side`** (خرید / فروش / میانی) اضافه شود.
2. **شرایط تجاری پلتفرم** (کارمزد، حدنصاب، وضعیت) به یک موجودیت مستقل تبدیل شود،
   چون چرخه‌ی عمرش با قیمت فرق دارد: قیمت هر ۳۰ ثانیه، کارمزد شاید ماهی یک‌بار.

### ۲.۲ موجودیت‌ها

```
Platform                       # ثابت، دستی نگهداری می‌شود
  slug                         # wallgold, milli, talasea, goldika, …
  name_fa, name_en
  website_url
  referral_url                 # لینک ثبت‌نام با کد معرف مالک — بند ۱۳، تصمیم ۲۱
  referral_param               # الگوی پارامتر هر سکو: referralCode / r / invitation
  legal_entity                 # برای صفحه‌ی «درباره‌ی این پلتفرم»
  data_policy                  # ALLOWED | RESTRICTED | PERMISSION_PENDING | BLOCKED
  is_listed                    # نمایش عمومی؟ فقط تابع data_policy (بند ۱۳، تصمیم ۲۰)

Quote                          # پرحجم، از کرالر می‌آید
  platform_slug
  instrument                   # GOLD_18K | ABSHODE_MITHQAL | SILVER_990 | XAU
  side                         # BUY | SELL | MID
  price                        # همیشه تومان، همیشه بر گرم (یا بر مثقال برای مظنه)
  raw_value, raw_scale         # مقدار خام و ضریب — برای auditability
  fetched_at

PlatformTerms                  # کارمزد و شرایط
  platform_slug
  buy_fee_percent, sell_fee_percent
  min_order_toman, max_order_toman
  physical_delivery_fee_percent, physical_delivery_min_unit
  buy_enabled, sell_enabled    # از disableBuy طلاسی و buyStatus وال‌گلد
  fee_source                   # API | MANUAL
  observed_at
```

سه نکته‌ی طراحی که عمداً این‌طور است:

**`raw_value` و `raw_scale` را نگه می‌داریم.** تحقیق نشان داد هر چهار پلتفرم
مقیاس متفاوتی دارند (×۱۰۰، ÷۱۰، ×۱، ×۱۰۰۰). اگر فقط عدد نرمال‌شده ذخیره شود و
یک روز ضریب اشتباه دربیاید، کل تاریخچه دور ریختنی است. با نگه‌داشتن خام، قابل
بازسازی است.

**`fee_source` مهم است.** کارمزد وال‌گلد و گلدیکا و طلاسی از API می‌آید و خودکار
به‌روز می‌شود؛ کارمزد میلی از صفحه‌ی وب خوانده شده و **دستی** است. اگر این تفکیک
نباشد، یک روز کارمزد میلی عوض می‌شود و ما ماه‌ها عدد غلط نشان می‌دهیم و دقیقاً
همان چیزی را از دست می‌دهیم که محصول رویش ساخته شده. عدد دستی باید تاریخ
مشاهده داشته باشد و در UI برچسب بخورد.

**`data_policy` روی پلتفرم.** تحقیق نشان داد شرایط استفاده‌ی گلدیکا صراحتاً
«قیمت» را دارایی خود می‌داند و ربات را «قابل پیگرد قانونی». باید بشود یک پلتفرم
را با یک تغییر مقدار از نمایش عمومی درآورد، بدون دیپلوی. این یک کلید حقوقی است،
نه یک فلگ فنی.

## ۳. معماری سرویس‌ها

```
   ┌─────────────┐
   │  پلتفرم‌ها   │  ۱۶ منبع عمومی بدون احراز هویت (بند ۱۲)
   └──────┬──────┘
          │ HTTP polling، ۳۰–۶۰ ثانیه
   ┌──────▼──────────────────────┐
   │  collector  (Python/async)  │
   │  ├ آداپتر به‌ازای پلتفرم      │
   │  ├ نرمال‌ساز واحد            │
   │  ├ sanity check تقاطعی       │
   │  └ health per source        │
   └───┬──────────────────┬──────┘
       │ قیمت جاری         │ snapshot تاریخی
   ┌───▼────┐        ┌─────▼──────┐
   │ Redis  │        │ PostgreSQL │
   │  TTL   │        │  history   │
   └───┬────┘        │  + blog    │
       │             └─────┬──────┘
   ┌───▼───────────────────▼──────┐
   │  web  —  SSR/ISR             │
   │  صفحات قابل کرال + بلاگ       │
   └──────────────────────────────┘
```

**چرا کالکتور از وب جداست:** کالکتور یک فرایند بلندمدت با حلقه‌ی asyncio است و
باید مستقل از ترافیک کاربر زنده بماند. اگر داخل فرایند وب باشد، هر ری‌استارت
یا اسکیل‌شدن وب یعنی چند نمونه‌ی موازی که همزمان به پلتفرم‌ها می‌زنند — همان
چیزی که باعث می‌شود IP ما بلاک شود. تفکیک، این را ساختاراً غیرممکن می‌کند.

**چرا Redis و Postgres هر دو:** Redis پاسخ صفحه‌ی اصلی را زیر یک میلی‌ثانیه
می‌دهد و TTL خودش نگهبان بیات‌شدن است. Postgres تاریخچه و بلاگ را نگه می‌دارد.
میلی از SQLite استفاده می‌کند و برایش کافی است، ولی ما بلاگ و صفحات سئویی هم
داریم و در حجم ~۳۰ هزار سطر در روز، Postgres انتخاب امن‌تری برای دو سال آینده است.

**الگویی که از کرالر میلی عیناً برمی‌داریم:** قیمت با TTL ذخیره شود ولی
`updated_at` **جدا و بدون TTL**. وقتی منبعی قطع می‌شود، به‌جای نمایش عدد بیات،
سایت می‌گوید «آخرین به‌روزرسانی: ۷ دقیقه پیش». برای سایتی که تمام ارزشش اعتماد
است، نمایش قیمت بیات بدون برچسب زمان یک باگ اعتماد است، نه یک باگ فنی.

## ۴. نرمال‌سازی و صحت‌سنجی

هر آداپتور موظف است ضریب تبدیل را **صریح** اعلام کند:

| پلتفرم | فیلد | ضریب → تومان/گرم |
|---|---|---|
| میلی | `data.price18` | ×۱۰۰ |
| گلدیکا | `data.mid_price` | ÷۱۰ |
| وال‌گلد | `result.price` | ×۱ |
| طلاسی | `price` | ×۱۰۰۰ |

**sanity check تقاطعی — الزامی.** چون تحقیق تأیید کرد پراکندگی واقعی زیر ۰٫۱٪
است، هر عددی که بیش از **۰٫۵٪** از میانه‌ی سایر منابع فاصله بگیرد، تقریباً
قطعاً خطای مقیاس یا endpoint خراب است، نه حرکت بازار.

قاعده: چنین عددی **منتشر نمی‌شود** و آلارم می‌دهد. یک قیمت غایب قابل توضیح است؛
یک قیمت ۱۰ برابر غلط روی سایتی که ادعای مقایسه دارد، اعتبار را یکجا می‌برد.

این چک تقریباً رایگان است چون بیش از ده منبع مستقل داریم که باید هم‌خوان باشند —
همان چیزی که مقایسه‌ای بودن محصول به ما هدیه می‌دهد.

## ۵. آداپتورها — وضعیت تأییدشده

> فهرست کامل ۱۶ منبع نسخه‌ی ۱ در بند ۱۲ است؛ جدول زیر چهار منبعی است که
> عمیق وارسی شده‌اند و الگوی پیاده‌سازی بقیه‌اند.

| پلتفرم | endpoint | خرید/فروش جدا؟ | کارمزد از API؟ | ریسک حقوقی |
|---|---|---|---|---|
| **وال‌گلد** | `api.wallgold.ir/api/v1/markets` | اسپرد صفر، کارمزد جدا | ✅ `otcFeeCoefficient` | 🟢 مستندات رسمی توسعه‌دهنده |
| **طلاسی** | `api.talasea.ir/api/market/getGoldPrice` | فقط mid | ✅ `fee` + `feeTable` | 🟢 بند ضد-scraping ندارد |
| **گلدیکا** | `goldika.ir/api/v2/public/price` | ✅ در `old_price` | ✅ `commission` | 🔴 صریحاً ممنوع کرده |
| **میلی** | `milli.gold/api/v1/public/milli-price/external` | فقط mid | ❌ دستی | 🟠 بند داده‌کاوی دارد |

نکاتی که مستقیماً به کد تبدیل می‌شوند:

- **وال‌گلد لنگر ماست.** تنها پلتفرمی است که پورتال توسعه‌دهنده‌ی رسمی دارد
  (`developers.wallgold.ir`)، `robots.txt`‌اش کاملاً باز است، و `24hVolume` را
  عمومی می‌کند. اول همین را پیاده کنیم.
- **`disableBuy`/`disableSell` طلاسی و `buyStatus`/`sellStatus` وال‌گلد** را حتماً
  بخوانید. در روزهای پرنوسان که پلتفرم‌ها فروش را می‌بندند، «الان کجا باز است»
  به‌تنهایی ترافیک می‌آورد و هیچ رقیبی آن را ندارد.
- **گلدیکا تا گرفتن اجازه‌ی کتبی با `data_policy = PERMISSION_PENDING` بماند** —
  کرال بشود، ذخیره بشود، ولی عمومی نمایش داده نشود.
- **endpoint ویجت میلی** (`.../widget/external`) سری زمانی ۱۵ دقیقه‌ای می‌دهد.
  برای نمودار تاریخچه در روز اول، بدون اینکه خودمان تاریخچه جمع کرده باشیم.

رفتار کرال در همه‌ی آداپتورها: User-Agent صادق و قابل شناسایی با URL تماس،
بازه‌ی ۳۰–۶۰ ثانیه (نه کمتر)، احترام به `robots.txt`، کش سمت خودمان. بار روی
سرور آن‌ها عملاً صفر می‌شود و انگیزه‌ی شکایت از بین می‌رود. این تصمیم فنی نیست،
مدیریت ریسک حقوقی است.

## ۶. سطح عمومی

> این بخش با تحقیق ۰۲ (سئو) قطعی شد. ارجاعات به بندهای همان سند است.

### ۶.۱ تأیید حیاتی: مدل کسب‌وکار از نظر گوگل مجاز است

مهم‌ترین ریسک وجودی پروژه بررسی شد و **منتفی است**. متن Spam Policies گوگل
مقایسه‌ی محصولات را صریحاً به‌عنوان نمونه‌ی **مجاز** نام می‌برد:

> "Good affiliate sites add value by offering meaningful content or features.
> Examples of good affiliate pages include offering **additional information
> about price**, original product reviews, rigorous testing and ratings,
> navigation of products or categories, and **product comparisons**."

یعنی دقیقاً همان کاری که می‌کنیم، در متن سیاست به‌عنوان مثال خوب آمده — نه بد.

**اما شرطش این است که ارزش‌افزوده قبل از انتشار موجود باشد.** آزمون گوگل: «آیا
کاربر دلیلی دارد که به‌جای رفتن مستقیم به سایت پلتفرم، اول اینجا بیاید؟» اگر
تنها چیزی که داریم بازنشر قیمت باشد، جواب نه است و مصداق thin affiliation
می‌شویم. این دقیقاً همان چیزی است که بند ۰ این سند گفت: قیمت مؤثر، اسپرد و
هزینه‌ی رفت‌وبرگشت **ویژگی اختیاری نیستند، شرط بقای سئویی‌اند**.

### ۶.۲ استراتژی رندر — تصمیم قطعی

> 🔄 **بازنویسی‌شده ۲۰۲۶-۰۸-۰۶ (تصمیم ۲۴): لایه‌ی وب از Next.js به تنکستک استارت
> مهاجرت کرد.** جدول زیر و واژه‌ی «ISR» تاریخچه‌ی تصمیم‌اند و دیگر پیاده‌سازی را
> توصیف نمی‌کنند. آنچه **جایگزین** شد:
>
> - در تنکستک استارت هیچ کش صفحه‌ای در مبدأ نیست: هر درخواست SSR می‌شود و
>   مستقیم از ردیس/پستگرس می‌خواند. نقشِ ISR را **کش لبه‌ی آروان** بازی می‌کند
>   با هدر `public, s-maxage=60, stale-while-revalidate=600, stale-if-error=86400`.
> - **هدر کش فقط به پاسخ ۲۰۰ داده می‌شود.** ۴۰۴ و ۵xx و هر چیز دیگر `no-store`
>   می‌گیرند — وگرنه لبه یک خطای گذرا را کش می‌کند و بند ۱۰ نقض می‌شود.
> - جای `generateStaticParams` را **آینه‌ی بیلد-تایم رجیستری گردآورنده** گرفت:
>   هویت صفحه (کدام اسلاگ وجود دارد) فراداده‌ی ثابت است و نباید به منبع زنده
>   گره بخورد. اسلاگ معتبرِ بی‌داده ⟸ ۲۰۰ با «قیمت در دسترس نیست» (قاعده‌ی ۵)؛
>   فقط اسلاگ ناشناخته ۴۰۴ می‌گیرد.
> - `revalidatePath` بی‌موضوع شد؛ اندپوینت `‎/api/revalidate-blog‎` عمداً با همان
>   قرارداد حفظ شد ولی دیگر چیزی برای باطل‌کردن ندارد (حداکثر ۶۰ ثانیه کش لبه).
>
> بقیه‌ی این بند — «cloaking نیست»، الزام `<time>` و به‌روزرسان کلاینت — بی‌تغییر
> برقرار است.

**ISR با `revalidate = 60` روی صفحات قیمت، به‌علاوه‌ی به‌روزرسانی زنده‌ی
کلاینت‌ساید بعد از hydration.** *(تاریخچه — به کادر بالا نگاه کنید.)*

| مسیر | استراتژی | دلیل |
|---|---|---|
| `/` داشبورد مقایسه | ISR ۶۰ ثانیه + به‌روزرسانی کلاینت | Googlebot HTML کامل با قیمت حداکثر ۶۰ ثانیه کهنه می‌بیند؛ کاربر قیمت زنده |
| `/[asset-slug]` — صفحه‌ی دارایی | ISR ۶۰ ثانیه + `generateStaticParams` | همان (طرح تخت، بند ۱۳ تصمیم ۱۱) |
| `/[platform-slug]` — صفحه‌ی سکو | SSG، بازتولید با `revalidatePath` هنگام ویرایش | محتوای تحریریه |
| `/blog/[slug]` | SSG کامل | بهترین Core Web Vitals |
| `/api/prices` | داینامیک، `Cache-Control: no-store` | فقط مصرف کلاینت |

سمانتیک ISR این را ممکن می‌کند: بعد از انقضای TTL، درخواست بعدی **نسخه‌ی کهنه را
فوری می‌گیرد** و بازتولید در پس‌زمینه انجام می‌شود. یعنی هیچ کاربر و هیچ خزنده‌ای
منتظر دیتابیس نمی‌ماند.

**این cloaking نیست** — تفاوت بین آنچه Googlebot و کاربر می‌بینند ناشی از *زمان*
است نه از تشخیص user-agent، و اگر Googlebot جاوااسکریپت را اجرا کند همان
به‌روزرسانی را می‌بیند. سیاست cloaking گوگل روی «قصد فریب» تمرکز دارد که اینجا
وجود ندارد.

**الزام همراه:** timestamp «آخرین به‌روزرسانی» باید داخل خود HTML رندرشده باشد
(`<time datetime="...">`). این همان چیزی است که در بند ۳ گفتیم Redis با کلید
`updated_at` جدا فراهم می‌کند — حالا معلوم شد کاربرد دومی هم دارد: نشان دادن
شفافیت به گوگل.

هدر CDN: `Cache-Control: public, s-maxage=60, stale-while-revalidate=300`

### ۶.۳ استک

**Next.js App Router.** دلیل انتخاب بر سایر گزینه‌ها:

- ISR با on-demand revalidation دقیقاً همین مسئله را حل می‌کند و مستنداتش صریح است.
- `sitemap.ts` و `robots.ts` و Metadata API سه جایی که بیشترین خطای سئو رخ می‌دهد
  را type-safe می‌کنند.
- `next/font` و `next/image` مستقیماً روی LCP و CLS اثر دارند — دو متریکی که برای
  این پروژه ریسک شناسایی‌شده‌اند.

گزینه‌ی JVM (Spring Boot + Thymeleaf) از نظر crawlability **بهترین** حالت ممکن
است چون صد درصد SSR است و هیچ پیچیدگی hydration ندارد. اگر تیم فقط Java بلد بود
انتخاب کاملاً معتبری بود و کار اضافه‌اش (کش و sitemap) چند ساعت است نه چند هفته.
چون تیم انتخاب آزاد دارد، Next.js را می‌گیریم.

> ⚠️ فایل `mazane.online.iml` در ریشه‌ی مخزن باقی‌مانده‌ی قصد اولیه‌ی JVM است و
> با این تصمیم بلااستفاده می‌شود.

### ۶.۴ لینک‌های ریفرال — الزام غیرقابل‌مذاکره

هر لینک درآمدزا **باید** `rel="sponsored"` داشته باشد. گوگل در پست رسمی ۲۶ ژوئیه
۲۰۲۱ صراحتاً از احتمال **manual action** برای سایت‌هایی که این کار را نمی‌کنند
گفته است. `nofollow` هنوز پذیرفتنی است ولی `sponsored` ترجیح صریح گوگل است.

```html
<a href="/go/wallgold" rel="sponsored nofollow noopener" target="_blank">…</a>
```

و مسیر ریدایرکت داخلی در `robots.txt` بسته شود:

```
Disallow: /go/
```

**یک تست خودکار در CI بنویسید که اگر لینک خروجی بدون `sponsored` پیدا شد شکست
بخورد.** یک خط کد است ولی وجودی — و دقیقاً از آن چیزهایی است که در بازنویسی‌های
بعدی بی‌سروصدا از بین می‌رود.

**قاعده‌ی مکمل که به مدل داده تحمیل می‌شود:** ترتیب نمایش پلتفرم‌ها **هرگز** بر
اساس کمیسیون نباشد، فقط بر اساس قیمت مؤثر. این هم اعتماد کاربر را حفظ می‌کند و
هم ادعای «مقایسه‌ی بی‌طرف» را راست نگه می‌دارد. یعنی `referral_url` در مدل
`Platform` نباید هیچ ورودی‌ای به منطق مرتب‌سازی داشته باشد.

### ۶.۵ داده‌های ساخت‌یافته

| نوع | حکم |
|---|---|
| `Organization` + `WebSite` (بدون `SearchAction`) | ✅ فقط صفحه‌ی اصلی |
| `BreadcrumbList` | ✅ همه‌جا |
| `BlogPosting` | ✅ مقالات |
| `Review` روی پلتفرم ثالث | ✅ فقط جایی که تست واقعی کرده‌ایم |
| `Product` + `AggregateOffer` | ⚠️ فقط صفحات دارایی مشخص |
| `Product` + `Offer` (merchant listing) | ❌ ما فروشنده نیستیم، واجد شرایط نیستیم |
| `FAQPage` · `HowTo` · `SearchAction` | ❌ **حذف شده‌اند** — وقت نگذارید |

سه نکته که مستقیماً به کد تبدیل می‌شوند:

1. **واحد پول در JSON-LD باید `IRR` باشد.** تومان کد ISO 4217 ندارد. مدل داده‌ی
   ما همه‌چیز را به **تومان** ذخیره می‌کند (بند ۲)، پس در لایه‌ی نمایش باید ×۱۰
   شود و `"priceCurrency": "IRR"` بخورد. اگر این تبدیل جا بیفتد، داده‌ی
   ساخت‌یافته‌ی ما ده برابر غلط خواهد بود.
2. **عدد داخل JSON-LD باید با عددی که کاربر روی صفحه می‌بیند یکی باشد.** چون
   صفحه ISR است و HTML ممکن است تا ۶۰ ثانیه کهنه باشد، JSON-LD هم باید **همان
   عدد کهنه** را داشته باشد، نه عدد زنده. یعنی JSON-LD باید در همان رندر سرور
   ساخته شود، نه در کلاینت.
3. **برای خودمان `AggregateRating` نگذاریم** — self-serving است و گوگل از ۲۴
   ژوئیه ۲۰۲۶ صریحاً منع کرده. نقد پلتفرم ثالث اشکالی ندارد.

### ۶.۶ فارسی، URL و نرمال‌سازی

- `<html lang="fa" dir="rtl">` و `og:locale=fa_IR`.
- **اسلاگ لاتین ترانویسی‌شده** (`/abshode`، `/talasea` — طرح تخت، بند ۱۳ تصمیم ۱۱) با `<h1>` و
  `<title>` کاملاً فارسی. دلیل اصلی: نیم‌فاصله (`U+200C`) در اسلاگ فارسی به
  `%E2%80%8C` تبدیل می‌شود که نامرئی است، کاربر نمی‌تواند تایپش کند، و دو URL
  تقریباً یکسان می‌سازد. اسلاگ لاتین هیچ کلمه‌ی کلیدی‌ای از دست نمی‌دهد چون گوگل
  رتبه را از محتوا و عنوان می‌گیرد نه از URL.
- **`normalizeFa()` روی مرز ورودی.** ی/ي/ى و ک/ك از نظر بایت متفاوت‌اند ولی تقریباً
  یکسان دیده می‌شوند. جست‌وجوی داخلی سایت و تطبیق نام پلتفرم‌ها در دیتابیس قطعاً
  می‌شکند مگر یک‌بار در ورودی نرمال کنیم. این الزام مهندسی است، نه قاعده‌ی گوگل.
- ارقام: فارسی در نمایش (با `Intl.NumberFormat('fa-IR')`)، **لاتین** در JSON-LD و URL.

### ۶.۷ `lastmod` در سایت‌مپ — تله‌ای که باید از آن دوری کرد

گوگل `lastmod` را فقط وقتی استفاده می‌کند که "consistently and verifiably
accurate" باشد. اگر چون قیمت هر دقیقه عوض می‌شود `lastmod` همه‌ی URLها را روی
`now()` بگذاریم، گوگل اعتمادش را به `lastmod` کل سایت از دست می‌دهد.

**قاعده: `lastmod` فقط با تغییر معنادار محتوا به‌روز شود** — افزوده شدن پلتفرم،
ویرایش تحلیل، انتشار مقاله. **نه با نوسان عدد قیمت.** (ضمناً `priority` و
`changefreq` را گوگل کلاً نادیده می‌گیرد.)

## ۷. الزامات حقوقی که به معماری تحمیل می‌شوند

> از تحقیق ۰۳. بخش حقوقی، برخلاف انتظار اولیه، **مانع نیست** — ولی چند الزام
> ساختاری تحمیل می‌کند که اگر از روز اول در معماری نباشند، بعداً بازسازی‌شان گران است.

### ۷.۱ انتشار قیمت جرم نیست — ولی محرک ریسک جای دیگری است

هیچ ماده‌ای در قانون مبارزه با قاچاق کالا و ارز یا جای دیگر، انتشار یا تجمیع
قیمت را جرم‌انگاری نکرده. تبصره ۱ ماده ۱۸ که فضای مجازی را مخاطب قرار می‌دهد،
موضوعش **عرضه یا فروش** است — و ما نه عرضه می‌کنیم نه می‌فروشیم.

ریسک واقعی، **فیلترینگ اداری** از مسیر کارگروه مصادیق است که حکم قضایی نمی‌خواهد.
اما محرکش انتشار قیمت **کذب** یا رفتار اخلال‌گرانه است، نه انتشار قیمت صحیح.
پلیس فتا صراحتاً گفته هدفش «درج قیمت‌های کذایی» است.

شاهد تعیین‌کننده: TGJU از ۱۳۹۷ تا امروز بدون وقفه فعال بوده، در حالی که سایت‌های
دیگری در همان دوره فیلتر شدند. سه ستون دفاعش: **ما فقط ناقلیم، منبع ما مراجع
مجاز است، ما معامله نمی‌کنیم.**

**الزام معماری ۱ — هرگز قیمت خودمان را تولید نکنیم.** هر عدد باید به یک پلتفرم
مشخص با timestamp نسبت داده شود. این مستقیماً بر طراحی بند ۴ اثر دارد:
**نتیجه‌ی sanity check تقاطعی نباید به‌عنوان «میانگین بازار» یا «نرخ مظنه» منتشر
شود.** آن محاسبه یک ابزار *داخلی* برای تشخیص خطاست، نه یک عدد قابل انتشار.
لحظه‌ای که سایت عدد مستقل خودش را اعلام کند، از «ناقل» به «مرجع قیمت‌گذاری»
تبدیل می‌شود و وارد قلمرو ریسک می‌شود.

**الزام معماری ۲ — آرشیو تغییرقیمت یک الزام حقوقی است، نه یک امکان جانبی.**
اگر روزی ادعای «قیمت کذب» مطرح شود، لاگ کامل هر عددی که نمایش داده‌ایم با منبع
و زمان، تنها دفاع مؤثر است. جدول `Quote` با `raw_value` و `raw_scale` (بند ۲.۲)
از قبل این را برآورده می‌کند — ولی حالا معلوم شد **نباید هرس شود**. سیاست
نگه‌داری داده باید «برای همیشه» باشد، نه «۹۰ روز».

### ۷.۲ مجوز سکوها — تصمیم: ردیابی نمی‌کنیم

**دستورالعمل اجرایی خرید و فروش برخط طلا و نقره** (مصوب هیئت وزیران
۱۴۰۴/۰۷/۲۷) فعالیت سکوهای بدون مجوز را عملاً غیرقانونی کرد، ولی بر اشخاص
ثالث و سایت‌های معرفی‌کننده تکلیفی نگذاشته — مصونیتی هم نداده.

> **تصمیم صاحب کسب‌وکار (بند ۱۳، تصمیم ۲۰): وضعیت مجوز سکوها به‌کلی کنار
> گذاشته شد.** سایت مجوز را ردیابی نمی‌کند، فهرست‌شدن به آن مشروط نیست و
> فیلدهای مجوز از مدل داده حذف شدند. ریسک حقوقی این انتخاب — معرفی فعالانه‌ی
> سکوی بدون مجوز در بدترین سناریو می‌تواند مصداق معاونت تلقی شود — یک‌بار
> مطرح و آگاهانه پذیرفته شد.

**الزامی که می‌ماند — نوار هشدار ماده ۵** (به مجوز ربطی ندارد): روی هر
صفحه‌ی ارجاع بیاید که معاملات طلای برخط صرفاً با پذیرش ریسک از سوی طرفین
انجام می‌شود و مشمول ضمانت دولت و نظام بانکی نیست. هم اعتبار می‌سازد و هم
مسئولیت را منتقل می‌کند.

### ۷.۳ چند تصمیم جانبی

- **بورس کالا و سکوها دو بازار مجزا هستند.** طلای آب‌شده‌ی خرد موضوع سکوهاست؛
  گواهی سپرده و صندوق‌های طلا موضوع بورس کالا. **در یک جدول مقایسه نکنیم** مگر
  با توضیح صریح تفاوت ماهیت.
- **ساماندهی بگیریم، ولی با دسته‌ی «اطلاع‌رسانی» نه «خبری».** معرفی خودمان به‌عنوان
  رسانه‌ی خبری، مجوز انتشار و یک لایه نظارت محتوایی اضافه می‌کند که به آن نیازی نداریم.
- **اینماد در فاز اول لازم نیست** — ابزار اعتمادسازی فروشگاه‌هایی است که پول
  می‌گیرند. فقط اگر بعداً درگاه پرداخت خواستیم الزامی می‌شود. پول تبلیغات را با
  قرارداد و فاکتور بگیریم، نه درگاه.
- **`mazane.ir` را هم ثبت کنیم و ۳۰۱ بدهیم به `.online`.** ارزان است، مالکیت را
  با کد ملی رسمی می‌کند و مسیر ساماندهی را ساده‌تر، و جلوی تصاحب دامنه‌ی مشابه را
  می‌گیرد.

### ۹.۱ درآمد روز اول وجود دارد

نسخه‌ی اول گفت هیچ پلتفرمی برنامه‌ی affiliate عمومی ندارد. **غلط بود.**

| پلتفرم | مدل | نرخ |
|---|---|---|
| **تکنوگلد** | سهم از کارمزد، **مادام‌العمر**، بدون سقف | **۳۰٪** |
| **اکوگلد** | سهم از کارمزد | **۳۰٪** |
| ملی‌گلد | CPA پس از احراز هویت | ۷ سوت — ⚠️ **سقف ۲۰ نفر**، مقیاس‌پذیر نیست |

مدل سهم از کارمزد به‌مراتب بهتر از CPA یک‌باره است: کارمزد تکنوگلد ~۰٫۶۲٪ هر سمت
است، پس ۳۰٪ آن ≈ **۰٫۱۹٪ از ارزش هر معامله، تکرارشونده تا هر وقت کاربر معامله
کند**. کاربری که ماهی ۱۰۰ میلیون تومان معامله کند ≈ ۱۹۰ هزار تومان درآمد ماهانه
تولید می‌کند.

به‌علاوه ثابت شد **زیرساخت ردیابی روی میلی، طلاسی، تکنوگلد و زرمینکس وجود دارد و
تجاری استفاده می‌شود** (از روی لینک‌های زنده‌ی یک رقیب). یعنی مذاکره با آن‌ها
درباره‌ی **نرخ** است، نه درباره‌ی **امکان‌پذیری**.

> **اثر بر معماری:** `referral_url` که nullable طراحی شده بود، برای تکنوگلد و
> اکوگلد از روز اول مقدار دارد. الگوی پارامتر هر پلتفرم فرق می‌کند
> (`referralCode`، `r`، `invitation`) پس باید per-platform ذخیره شود، نه یک قالب
> مشترک. گلدیکا اصلاً پارامتر ارجاع ندارد.
>
> **هشدار مدل مالی:** نرخ ۳۰٪ فقط برای دو پلتفرم کوچک‌تر تأیید شده. به بقیه
> تعمیمش ندهید تا قرارداد امضا شود.

نظرات کاربران، و شمارش معکوس ۶۰ ثانیه‌ای.

دو رقیب دیگر: `talamarketcap.com` (در لحظه‌ی بازدید جدول قیمتش `NaN` نشان می‌داد
— خراب است) و `gheymat.online` (مدلش فروش داده به شرکت‌هاست، رقیب لایه‌ی درآمد نیست).

**این یعنی ایده اعتبارسنجی شده، ولی «اولین نفر بودن» ممکن نیست.** برنده شدن باید
از راه اجرا باشد نه ایده. پنج شکافی که زرایران پر نکرده و باید مشخصات محصول ما شوند:

1. **پوشش.** زرایران **۶** پلتفرم دارد؛ تحقیق **۲۳** پلتفرم شناسایی کرد. وال‌گلد،
   اکوگلد، بازر، طلاین، داریک، همراه‌گلد، ملی‌گلد و دیجی‌کالا اصلاً در آن نیستند.
   این تنها برتری‌ای است که **بلافاصله** و بدون مذاکره به‌دست می‌آید.
2. **وضعیت زنده‌ی سرویس.** `disableBuy`/`disableSell` طلاسی و `buyStatus`/`sellStatus`
   وال‌گلد را **هیچ رقیبی استفاده نمی‌کند**.
3. **کارمزد پلکانی بر اساس مبلغ کاربر.** رقبا بازه نشان می‌دهند («۰٫۵٪ الی ۱٫۲٪»).
   ماشین‌حسابی که بپرسد «چقدر می‌خواهی معامله کنی؟» و **عدد دقیق** بدهد، جهش کیفی
   است. این مستقیماً `feeTable` طلاسی را به یک ویژگی محصول تبدیل می‌کند.
4. **هزینه‌ی تحویل فیزیکی.** هیچ‌کس کنار هم نگذاشته — و اعداد فاحش‌اند: دیجی‌کالا
   عملاً **۸٪** می‌گیرد (۴۰۰ میلی‌گرم از هر شمش ۵ گرمی) در برابر ۳٪ میلی.
5. **تمایز مدل معاملاتی.** داریک **دفتر سفارش** است نه OTC؛ `bestSell` گاهی `null`
   است. گذاشتنش در همان ستون با dealerها دو خطا تولید می‌کند: قیمتی که ممکن است
   نقدینگی نداشته باشد، و اسپردی که هم‌جنس بقیه نیست. **ردیف جدا یا برچسب صریح لازم دارد.**

### ۹.۳ قاعده‌ی عضویت در جدول مقایسه

تحقیق با ۵ اسنپ‌شات هم‌زمان از ۱۳ پلتفرم آزمود که آیا برندهایی با موتور مشترک
وجود دارند. نتیجه: شاهدی پیدا نشد. ولی قاعده باید در کد مکتوب شود:

> یک ردیف فقط وقتی وارد جدول می‌شود که **(۱) دامنه‌ی مصرف‌کننده‌ی مستقل خودش را
> داشته باشد و (۲) endpoint قیمت روی همان دامنه منتشر کند.**

برندهای white-label طلاسی (اسنپ‌پی، بله، تارا، علی‌بابا گلد و…) هیچ‌کدام این دو
شرط را ندارند، پس خودبه‌خود بیرون می‌مانند. بدون این قاعده، به‌محض اینکه کسی
بخواهد «علی‌بابا گلد» را اضافه کند، محصول شروع می‌کند چند front-end یک موتور را
به‌عنوان قیمت‌های رقیب نشان دادن — که همان حالت شکستی است که نمی‌شود با آن لانچ کرد.

نکته‌ی آخر: بیرون ماندن این برندها درآمدی را هم از دست نمی‌دهد — مسیر درآمد
روز اول برنامه‌های عمومی تکنوگلد و اکوگلد است (بند ۹.۱) و لینک معرف روی
همه‌ی سکوهای مستقل از مسیر `/go/` می‌رود (بند ۱۳، تصمیم ۲۱). مذاکره‌ی
مستقیم فقط برای سکوهایی لازم است که وضعیت ریفرال‌شان در جدول بند ۱۲.۱ هنوز
«بررسی شود» است.

## ۱۰. میزبانی — حل تعارض دو تحقیق

تحقیق ۰۲ (سئو) و ۰۳ (زیرساخت) به نتیجه‌ی **متضاد** رسیدند. هر دو استدلال درستی
داشتند و تعارض واقعی بود، نه سوءتفاهم:

| | توصیه | استدلال |
|---|---|---|
| تحقیق ۰۲ | هاست **خارج** | مستندات خود گوگل: خطای شبکه/DNS هم‌ارز ۵xx است و «Already indexed URLs that are unreachable will be removed from Google's index **within days**». Googlebot از خارج می‌خزد؛ origin ایرانی در قطعی یا فیلترینگ خروجی از دسترسش خارج می‌شود |
| تحقیق ۰۳ | هاست **داخل** | ۱۰۰٪ مخاطب ایرانی است؛ سایت قیمت لحظه‌ای حساس‌ترین نوع به تأخیر است؛ ترافیک داخلی نیم‌بها؛ Cloudflare و Vercel عملاً اپراتور ایرانی را نمی‌پذیرند |

### ۱۰.۱ کلید حل تعارض

جمله‌ی تعیین‌کننده در تحقیق ۰۲:

> اگر CDN جلوی سایت باشد، **آن CDN است که باید برای Googlebot در دسترس باشد،
> نه origin.**

و داده‌ی تعیین‌کننده در تحقیق ۰۳: **آروان اکثر PoPهایش را خارج از کشور گذاشته**
و جزو ۱۰ سرویس‌دهنده‌ی پرترافیک جهان است.

این دو کنار هم یعنی تعارض ظاهری است: **origin داخل ایران + CDN آروان** هر دو
نیاز را هم‌زمان برآورده می‌کند. Googlebot به لبه‌ی خارجی آروان می‌خورد و اصلاً
به origin نمی‌رسد؛ کاربر ایرانی هم از PoP داخلی سرویس می‌گیرد.

### ۱۰.۲ شرط سختی که این ترکیب را ایمن می‌کند

این معماری **فقط و فقط** وقتی امن است که یک چیز برقرار باشد:

> **CDN باید وقتی origin در دسترس نیست، نسخه‌ی کش‌شده‌ی کهنه را با کد ۲۰۰ سرو کند.**

اگر آروان در قطعی origin به Googlebot خطا برگرداند، دقیقاً همان سناریوی «within
days» رخ می‌دهد و هیچ‌کدام از مزایای بالا اهمیتی ندارد. **این تنها نقطه‌ی شکست
معماری میزبانی است.**

خبر خوب: ISR ذاتاً در همین جهت کار می‌کند — HTML آخرین رندر موفق روی لبه می‌ماند.
ولی رفتار fallback آروان در قطعی origin باید **قبل از لانچ عملاً تست شود**، نه فرض.

> ✅ **آزموده شد (۲۰۲۶-۰۸-۰۶، روی استقرار واقعی):** با «دسترسی همیشگی» فعال
> در آروان + قانون صفحه‌ی کش برای `mazane.online/*`، مبدأ عمداً خوابانده شد و
> لبه در تمام مدت **۲۰۰ کش‌شده (HIT)** سرو کرد؛ پس از بازگشت مبدأ هم سالم.
> نکته‌ی باز: عمر کش را TTL قانون صفحه تعیین می‌کند نه `s-maxage` مبدأ
> (سنجش ۷۵ثانیه‌ای)؛ فعلاً ۱ ساعت است — اگر گزینه‌ی دقیقه‌ای در پنل هست،
> کمینه انتخاب شود تا کهنگی HTML برای خزنده به هدف ~۶۰ ثانیه نزدیک بماند.

سه الزام عملیاتی که از این نتیجه می‌گیریم:

1. **هرگز برای شکست کالکتور ۵xx برنگردانید.** اگر منبع قیمت قطع شد، صفحه‌ی
   کش‌شده با برچسب «آخرین به‌روزرسانی: N دقیقه پیش» را با **۲۰۰** سرو کنید.
   برگرداندن ۵۰۳ به‌خاطر قطعی یک منبع فرعی، سایت را در مسیر «persistently
   return a server error» می‌گذارد. این مستقیماً طراحی بند ۳ را تأیید می‌کند:
   قیمت `null` با `updated_at` معتبر، نه خطا.
2. **مانیتورینگ در دسترس‌بودن باید از خارج ایران باشد**، نه از داخل. تنها چیزی
   که اهمیت دارد این است که آیا Googlebot می‌تواند برسد یا نه.
3. **تأیید مالکیت Search Console با DNS TXT.** تنها روشی است که به دسترسی مداوم
   ما وابسته نیست و با تغییر میزبانی نمی‌شکند.

### ۱۰.۳ دو نکته‌ی جانبی که قطعی شدند

- **Cloudflare و Vercel گزینه نیستند.** هر دو عملاً اپراتور ایرانی را نمی‌پذیرند
  (Vercel حتی قالب آماده‌ی firewall برای مسدودسازی کشورهای تحریم‌شده منتشر کرده).
  مجوز عمومی OFAC D-2 مبنای حقوقی می‌دهد ولی تصمیم تجاری هر شرکت جداست.
- **ابزار International Targeting در Search Console از ۲۲ سپتامبر ۲۰۲۲ حذف شده.**
  هیچ کلیدی نیست که «این سایت برای ایران است» را اعلام کند. سیگنال واقعی همان
  زبان محتوا، `lang="fa"`، ارز، و لینک‌های ورودی ایرانی است.

## ۱۱. املای برند — ✅ تصمیم‌گیری شد: مظنه آنلاین

تحقیق ۰۲ این را با داده‌ی زنده از endpoint عمومی autocomplete گوگل
(`hl=fa&gl=ir`) آزمود، نه با حدس.

**املای درست «مظنه» است** (ریشه‌ی عربی مَظِنّة؛ در بازار طلا یعنی قیمت یک مثقال
طلای آب‌شده). «مضنه» غلط املایی رایج است.

**و گوگل خودش این را اصلاح می‌کند:** برای کوئری «مضنه طلا»، **هر ۱۰ پیشنهاد
بدون استثنا** «مظنه طلا …» برمی‌گردد. کل درخت پیشنهاد «مضنه» به «مظنه» هدایت
می‌شود.

سه نتیجه:

1. **از نظر ترافیک ارگانیک این دو کوئری جدا نیستند** — گوگل کاربر «مضنه» را به
   نتایج «مظنه» می‌برد. یعنی انتخاب املا ترافیک را نصف نمی‌کند.
2. **«مظنه» فرم غالب است** و کل تقاضا آنجاست.
3. ولی «مضنه» تقاضای مستقل خودش را هم دارد — و کوئری واقعی **«مضنه یا مزنه»**
   وجود دارد، یعنی مردم فعالانه درباره‌ی املای درست سردرگم‌اند.

> **تصمیم نهایی (مصاحبه‌ی ۲۰۲۶-۰۸-۰۶): برند «مظنه آنلاین» است — املای درست.**
> «مضنه» در `alternateName` اسکیمای `Organization` می‌آید و فقط به‌عنوان غلط
> املایی در محتوا هدف‌گیری می‌شود (صفحه‌ی «مظنه چیست» هر دو املا را پوشش می‌دهد)،
> هرگز در خود برند. دامنه‌ی `mazane.online` با هر دو می‌خواند.

   (افزودن سایت به پیکربندی کدی موجود)؛ (۲) رم و پردازنده تنگ است — ساخت
   نکست‌جی‌اس باید بیرون از سرور انجام شود و روی سرور فقط خروجی اجرا شود.
6. **محتوای بلاگ: تولید انبوه با AI** (انتخاب صاحب کسب‌وکار؛ نگرانی مطرح و رد
   شد — ادامه بدهید).
7. **منبع محتوا: ۱۰۰٪ داده‌محور.** هیچ پست توضیحی عمومی نه. پست‌های لانچ از
   داده‌ی مقطعی (مقایسه‌ی کارمزد، حدنصاب، هزینه‌ی رفت‌وبرگشت)؛ پست‌های سری زمانی
   از ~هفته‌ی چهارم.
8. **استک: کالکتور Python + وب Next.js App Router؛ یک مخزن، دو فرایند.**
   قاعده‌ی سخت: هر مقدار مشتق (قیمت مؤثر، هزینه‌ی رفت‌وبرگشت) **فقط** در کالکتور
   محاسبه و ذخیره می‌شود. لایه‌ی وب فقط می‌خواند. هیچ فرمولی دو پیاده‌سازی ندارد.
9. **تفکیک کامل تبلیغ و تحریریه.** «پیشنهاد سردبیر» تحریریه است، معیارهایش منتشر
   می‌شود، هرگز فروخته نمی‌شود. تبلیغ پولی از نظر بصری متمایز، با برچسب «تبلیغ»،
   `rel="sponsored"`، و هرگز بر ترتیب جدول اثر ندارد.
10. **پوشش دارایی: هرچه هر پلتفرم عرضه می‌کند.** قاعده‌ی افزوده: دارایی‌ای که فقط
    یک پلتفرم دارد **صفحه‌ی مقایسه‌ی اختصاصی نمی‌گیرد** — کرال و ذخیره می‌شود و
    در صفحه‌ی همان پلتفرم نمایش می‌یابد. با آمدن پلتفرم دوم، صفحه خودکار ساخته و
    ایندکس می‌شود. `instrument` به موجودیت کامل تبدیل می‌شود (واحد، عیار، ارز،
    شمار پلتفرم‌های پشتیبان به‌عنوان دروازه‌ی انتشار).
11. **طرح URL: تخت، اسلاگ لاتین ترانویسی‌شده.** مهار ریسک برخورد: جدول مرکزی
    `slug` با قید یکتایی بین دارایی‌ها، پلتفرم‌ها و پست‌ها + کلمات رزرو
    `blog`، `go`، `api`، `sitemap.xml`، `robots.txt`، `_next`، `about`.
12. **🔄 جایگزین‌شده در دور دوم با تصمیم‌های ۲۰ و ۲۲.** معیار مجوزمحور و فهرست
    هفت‌تایی لانچ منسوخ شد: همه‌ی ۱۴ سکوی بند ۱۲ منتشر می‌شوند،
    `is_listed ⟺ data_policy = ALLOWED`، و تنها استثنا گلدیکاست
    (`PERMISSION_PENDING` تا اجازه‌ی کتبی).
13. **بازه‌ی polling: ۳۰ ثانیه.** پیامد: چون ISR ۶۰ ثانیه است، به‌روزرسان
    کلاینت‌ساید **الزامی** شد — endpoint سبک JSON که هر ۳۰ ثانیه poll می‌شود و
    اعداد را درجا عوض می‌کند؛ ISR پوسته را هر ۶۰ ثانیه بازمی‌سازد.
    نگه‌داری (پیشنهاد مهندسی، قابل بازبینی): خام ۹۰ روز با حذف مقادیر تکراری
    متوالی + rollup ساعتی برای همیشه. ⚠️ توجه: بند ۷.۱ آرشیو «برای همیشه» را
    الزام حقوقی می‌داند — rollup ساعتی + `raw_value` نگه‌داشته‌شده باید این را
    برآورده کند؛ سیاست دقیق هرس هنوز نهایی نیست.
14. **دسترسی Google Search Console تأییدنشده — صاحب کسب‌وکار باید تست کند.**
    پیش‌نیاز مسدودکننده. بیمه‌ی معماری صرف‌نظر از نتیجه: لاگ بازدیدهای Googlebot
    در origin با تأیید reverse-DNS (معادل self-hosted برای Crawl Stats). ثبت
    سایت‌مپ از طریق خط `Sitemap:` در `robots.txt` هم ممکن است.
15. **جایگاه‌های تبلیغ از نسخه‌ی ۱ در layout رزرو می‌شوند** — ارتفاع ثابت، تا
    فروش با پیشنهاد سردبیر پر می‌شوند. جلوی CLS بعدی را می‌گیرد و دموی جایگاه
    زنده می‌دهد.
16. **خط لوله‌ی محتوا: تمام‌خودکار با دروازه‌ی اعتبارسنجی** (انتخاب صاحب
    کسب‌وکار به‌جای بازبینی انسانی؛ نگرانی مطرح و رد شد). پس دروازه باید سخت‌گیر
    باشد:
    - هیچ عددی هرگز از مدل نمی‌آید. اعداد slot‌اند و بعد از تولید سمت سرور پر
      می‌شوند؛ هر رقم بیرون از slot ⟸ رد کل پست.
    - ادعاها («ارزان‌ترینِ این هفته X بود») با کوئری مشتق می‌شوند، نه ادعای مدل.
    - چک میانه‌ی تقاطعی باید برای هر پلتفرم ارجاع‌شده در بازه پاس شود.
    - برای بازه‌ای که هر پلتفرم ارجاع‌شده گپ داده دارد، پستی تولید نمی‌شود.
    - آستانه‌ی شباهت متنی با پست‌های موجود ⟸ رد.
    - سقف انتشار روزانه سمت سرور، مستقل از تعداد پیش‌نویس‌ها.
    - پس‌گیری تک‌فرمانی: `noindex` + حذف از سایت‌مپ.
17. **مولد محتوا روی ماشین محلی صاحب کسب‌وکار، زمان‌بندی‌شده.** مدل‌ها:
    **`gemini-3.6-flash`** برای نثر، **`gemini-3.5-flash-lite`** برای کارهای
    مکانیکی (متا، واریانت عنوان، پیش‌غربال شباهت). *(اصلاح ۲۰۲۶-۰۸-۰۶: مدل
    ۲.۵ لایتِ تصمیم اولیه برای کلیدهای تازه بسته شده بود؛ با کلید واقعی
    سنجیده و به ۳.۵ لایت به‌روز شد. کلید در `‎.env` محلیِ گیت‌ایگنورشده است.)*
    - معماری نجات «لپ‌تاپ شاید خاموش باشد»: **مولد صف پیش‌نویس را پر می‌کند؛
      سرور با آهنگ ثابت خالی می‌کند.** عمق هدف ۱۴ روز، هشدار زیر ۵ روز. کلید
      Gemini هرگز از لپ‌تاپ خارج نمی‌شود.
    - واقعیت‌های تأییدشده: ایران جزو ۱۹۰+ منطقه‌ی پشتیبانی‌شده‌ی API جمینای
      نیست؛ اشتراک Google AI Pro/Ultra فقط دسترسی چت/AI-Studio می‌دهد، نه API
      (آن کلید AI Studio + Cloud Billing جدا می‌خواهد). هزینه در ۱۰ پست/روز
      ~۶ دلار/ماه روی 3.6 Flash — هزینه فاکتور تصمیم نیست، کیفیت نثر فارسی هست.
    - موتور نوشتن: LLM با قالب داده‌ی سخت؛ واقعیت‌ها قفل، نثر آزاد.
18. **جدول اصلی: نمای تک‌عددی.** «برای یک گرم طلا چقدر می‌پردازی؟» — صعودی بر
    اساس هزینه‌ی مؤثر، هر ردیف با دلتای نسبت به ارزان‌ترین. بقیه‌ی ستون‌ها به
    جزئیات بازشونده و صفحه‌ی پلتفرم می‌روند. مستقیم به `Product` +
    `AggregateOffer` با `lowPrice`/`highPrice` نگاشت می‌شود.
19. **🔄 اصلاح‌شده در ادامه‌ی مصاحبه (۲۰۲۶-۰۸-۰۶): هر دارایی فقط یک صفحه دارد.**
    میانگین خرید و فروش به‌عنوان قیمت محاسبه می‌شود. طرح دو صفحه‌ی مجزای
    خرید/فروش (نسخه‌ی قبلی این تصمیم) کنار گذاشته شد؛ در نتیجه سؤال «آدرس‌دهی
    صفحه‌ی فروش در URL تخت» هم منتفی است — هر دارایی همان یک اسلاگ را دارد
    (`/noghre`). حجم انتظاری: ۳–۵ صفحه‌ی دارایی + ~۱۳ صفحه‌ی سکو (همه به‌جز
    گلدیکا) + بلاگ.
    - وضعیت باز/بسته‌ی خرید و فروش (`disableSell` طلاسی، `sellStatus` وال‌گلد)
      همچنان مزیت رقابتی است و روی همین تک‌صفحه به‌صورت نشان می‌آید.
    - **کارمزد در قیمت‌های نمایشی تاثیر داده می‌شود** (پاسخ صریح صاحب
      کسب‌وکار): قیمت‌های جدول «مؤثر خرید» و «مؤثر فروش»‌اند، نه قیمت اسمی.
      قیمت مرجع هر پلتفرم = میانگین همین دو قیمت مؤثرِ خودش. مرتب‌سازی مطابق
      تصمیم ۱۸ می‌ماند: صعودی بر اساس قیمت مؤثر خرید، با دلتا نسبت به
      ارزان‌ترین.
    - قید بند ۷.۱ برقرار است: **میانگین بین‌پلتفرمی هرگز منتشر نمی‌شود.** هر
      میانگین فقط به‌ازای یک پلتفرم محاسبه و به همان پلتفرم منتسب می‌شود؛
      قیمت مرجع صفحه در داده‌ی ساخت‌یافته با بازه‌ی `lowPrice`/`highPrice`
      در `AggregateOffer` بیان می‌شود، نه با یک عدد سراسری.
20. **مجوز کسب‌وکارها به‌کلی کنار گذاشته شد (دور دوم، ۲۰۲۶-۰۸-۰۶).** سایت
    وضعیت مجوز سکوها را ردیابی نمی‌کند، فهرست‌شدن به آن مشروط نیست، فیلدهای
    مجوز و استعلام ماهانه حذف شدند و لایه‌ی انطباق قدیم بند ۱۲ با فهرست
    منابع جایگزین شد. ریسک حقوقی این انتخاب (بند ۷.۲) یک‌بار مطرح و
    آگاهانه پذیرفته شد.
21. **لینک ریفرال روی همه‌ی سکوها.** هر کلیک خروجی از مسیر `/go/<slug>` با
    کد معرف مالک می‌رود تا ثبت‌نام به نام او ثبت شود. کد معرف و الگوی
    پارامتر هر سکو (referralCode / r / invitation؛ گلدیکا پارامتر ندارد) در
    `Platform.referral_url` و `referral_param` نگه‌داری می‌شود؛ تا وقتی کد
    معرف سکویی گرفته نشده، لینک مستقیم می‌رود. **کدهای معرف را صاحب
    کسب‌وکار تهیه و تحویل می‌دهد.** الزامات بند ۶.۴ پابرجاست:
    `rel="sponsored"`، بستن `/go/` در `robots.txt`، تست خودکار در CI.
22. **فهرست منابع = همه‌ی منابع پشتیبانی‌شده در خزنده‌ی مرجع، به‌جز فراز و
    نوبیتکس:** ۱۴ سکو + ۲ مرجع قیمت. جدول کامل در بند ۱۲.
23. **قیمت مرجع سکو، و نمودار صفحه‌ی اصلی** (مصاحبه‌ی طراحی، ۲۰۲۶-۰۸-۰۶):
    - **قاعده‌ی قطعی مقدار:** اگر سکو **یک** عدد منتشر کند، همان عدد قیمت مرجع
      اوست؛ اگر **دو** عدد منتشر کند، میانگین آن دو. پیامد عمدی: سکوی
      کارمزدنامعلوم (ملی‌گلد، دیجی‌کالا، همراه‌گلد، اینوی) هم قیمت مرجع دارد.
      دفتر سفارش یک‌طرفه قیمت مرجع ندارد — جعل نمی‌شود.
    - قیمت مرجع از یک `computed_field` به **سطر ذخیره‌شده** (`Side.MEAN`) ارتقا
      یافت تا تاریخچه و تجمیع ساعتی داشته باشد (مهاجرت ۰۱۳). همچنان به یک سکوی
      مشخص منتسب است و **میانگین بین‌سکویی نیست** (قاعده‌ی ۴، بند ۷.۱).
    - **نمودار صفحه‌ی اصلی:** خطی، ۲۴ ساعته، محور مطلق زوم‌شده، هر خط قیمت مرجع
      یک سکو. پنج سکوی ثابتِ انتخاب مالک: میلی، ملی‌گلد، طلاسی، طلاین، وال‌گلد.
    - ⚠️ **معامله‌ی آگاهانه:** با کارمزد متقارن، میانگین دو سمت مؤثر ریاضی‌وار
      برابر قیمت اسمی می‌شود (با داده‌ی زنده‌ی ۲۰۲۶-۰۸-۰۶ برای هر ۱۲ سکو تأیید
      شد). یعنی **کارمزد در نمودار دیده نمی‌شود** و مقایسه‌ی مؤثر کار جدول است.
      این نگرانی یک‌بار با عدد به مالک گزارش شد و او آگاهانه میانگین را انتخاب کرد.
24. **مهاجرت لایه‌ی وب از Next.js به تنکستک استارت (۲۰۲۶-۰۸-۰۶).** فرانت تازه را
    مالک با Lovable ساخت و همان مبنا شد؛ طراحی و اجزا از آنجا آمدند و تمام
    قابلیت‌های موجود داخلش پورت شدند (هیچ‌کدام از ۱۱ مسیر حذف نشد).
    - پیامدهای معماری در بند ۶.۲ بازنویسی شده‌اند: بی‌کش بودن مبدأ، نقش
      پررنگ‌تر کش لبه، و آینه‌ی بیلد-تایم رجیستری به‌جای `generateStaticParams`.
    - **درس مهاجرت که باید بماند:** گره‌زدن *هویت صفحه* به منبع *زنده* باعث شد
      در قطعی ردیس هر ۱۴ صفحه‌ی دارایی و سکو ۴۰۴ بدهند و همان ۴۰۴ در لبه کش شود
      — نقض قاعده‌ی ۵ و خطر مستقیم برای ایندکس. پیش از انتشار رفع شد. هر بازنویسی
      بعدی باید همین سناریو را (منبع مرده ⟸ ۲۰۰ کهنه) واقعاً بیازماید.
    - خروجی نیترو با پریست `node-server` است، نه Cloudflare Workers (پیش‌فرض).
      فونت وزیرمتن خودمیزبان شد و تله‌متری Lovable حذف — سایت به هیچ دامنه‌ی
      بیرونی وابسته نیست.

### ۱۳.۱ — اقدام‌های معوق صاحب کسب‌وکار

1. تست دسترسی گوگل سرچ کنسول (پراپرتی آزمایشی + تأیید دی‌ان‌اس) — آیتم ۱ سند ۰۲.
2. روشن کردن اینکه خرید «جمینای» چه بوده — اشتراک یا کلید API با صورتحساب.
3. تأیید اینکه آروان در قطعی origin کش کهنه را با کد ۲۰۰ سرو می‌کند
   (پیش‌شرط بند ۱۰.۲).
4. تحویل لینک‌های معرف سکوها — صاحب کسب‌وکار به‌عهده گرفته (تصمیم ۲۱).
   برای دیجی‌کالا: ایمیل به افیلیو که آیا طلای دیجیتال کمپین همکاری دارد.
5. تکرار تست استقلال قیمت در ساعات بازار (۱۰:۰۰–۱۷:۰۰) — اجرای ~۰۲:۰۰ برای
   طلاسی/میلی نامعلوم بود.
6. درخواست اجازه‌ی کتبی از گلدیکا برای نمایش عمومی داده.
